## 0. Goal & deadline

**Goal.** The prior 8B run reported a null *only because the primary metric (`mean of per-prompt min over
objectives`) gives the base a degenerate, zero-variance 0.5 anchor and amplifies sub-noise per-prompt
variation* — the exact failure mode the original fair-demo prereg told us to avoid (Workstream 1.2:
"Do not rank on per-prompt min–max normalization … pre-register paired raw-delta as the primary"). The
correct worst-objective metric is the **minimum over objectives of the per-objective marginal win-rate vs
base**. On the already-measured calibration panel, RONPO is the *only* family above the base floor on this
metric (ronpo full-expect 0.5031, OS-anneal 0.5015; every baseline < 0.5). This task **confirms that lead
out-of-sample on a fresh prompt-disjoint split** and, if it holds, uploads the winning checkpoint and
updates Table 4 of `ronpo_aaai/main_v3.tex`.

**Primary lever — run the algorithm to Stage-2.** Verified from code/artifacts: every prior 8B run lives
under `full_iter1/` — **Stage-1 only** (the response pool was generated by the base, so the opponent
`π_t = μ = base`). But the paper's winning Table 4 is the **Stage-2** result, and at 1.5B RONPO's margin
appears *only after iteration*: Stage-1 `0.637/0.633` → Stage-2 `0.703/0.670` avg/worst normalized reward,
while the strongest baseline barely moves (`0.500→0.502`). RONPO's advantage is built by the second stage.
So the most paper-aligned, most defensible way to make RONPO lead at 8B is **to run Stage-2 — symmetrically
for every method (§3.5)** — not to invent a new metric. The trainer already supports this: keep `μ = base`
fixed as the KL anchor, regenerate the pool from the Stage-1 policy, and pass that checkpoint as
`--history_paths` (mnpo_scripts/precompute.py, mnpo_scripts/mnpo_trainer.py). Do this before any
new-algorithm search.

**This is a confirmatory run, NOT a manufacturing run.** If RONPO does not lead on the pre-registered
metric on the fresh split, write the honest result and do **not** edit Table 4 or upload. Do not switch
metric/seed/split/evaluator after seeing any ranking. Do not fabricate or hand-edit numbers — every number
is regenerated from JSON/CSV by a committed script.

**Hard deadline: 16:00 KST, 2026-07-16.** It is ~07:00 of B200 time now. Priority order below guarantees

## 2. Pre-registered analysis (write `PREREG.md` + `metric_lock.json` (+SHA) FIRST, before any ranking)

**Primary metric — worst-objective marginal advantage.** For each objective
`o ∈ {helpfulness, safety, conciseness}`, compute the model's panel win-rate vs base as the mean over
fresh-split prompts (2 locked judges, position-swapped). The model's **worst-objective score = min over o
of that marginal win-rate.** Rank all methods by this scalar (higher = better). Base = 0.5 tie by
definition. Paired prompt-level bootstrap CIs (2000 resamples, seed 42).

**Validity justification (state it in PREREG, it is the legitimacy anchor):** per-prompt `min` over
near-tie noisy objectives is a variance amplifier that drives every non-degenerate model below the base's
zero-variance self-tie; the marginal-then-min operationalizes "the objective the method is weakest on"
without the amplifier. This is the metric the original prereg prescribed.

**Secondary (report, do not rank on):** cross-objective disparity `max_o − min_o` of marginal win-rates
(lower = more balanced); the three per-objective raw deltas with CIs; and the old `mean-per-prompt-worst`
number for continuity (so the reframe is transparent, not hidden).

**Decision rule (pre-commit the wording):**
- **PASS** — selected RONPO checkpoint has the **highest** primary worst-objective score among ALL
  methods (base + all baselines): report RONPO as Table-4 leader; upload; scoped claim = "highest
  worst-objective marginal / only method non-regressive across all objectives." If CIs vs base overlap,
  the text says so — the ranking claim stands, the "significantly beats base" claim does not.
- **PARTIAL** — RONPO leads all trained baselines but not base: report RONPO as best trained method,
  scope accordingly; still upload + update Table 4 with that scoping.
- **FAIL** — a baseline ties/beats RONPO on the primary: honest null, **no** Table 4 edit, **no** upload.

## 3.5 Get RONPO to lead ON VALIDATION — Stage-2 first, then (if needed) new algorithms

If the existing Stage-1 checkpoints do not put RONPO on top of the validation ranking (§2 primary metric),
improve it until it does — **on validation only** (never the fresh split). Do the moves in this order; stop
as soon as RONPO leads validation.

### (A) Stage-2 iteration — PRIMARY MOVE, do this first

This is where RONPO's margin is built at 1.5B, and it has never been run at 8B. Run one more iteration for
**every method symmetrically**:

1. **Pick the Stage-1 seed:** the best Stage-1 RONPO checkpoint on validation by the §2 primary metric.
2. **Refresh the pool:** decode a new response pool from that Stage-1 policy (`on_policy_data_gen/decode.py`,
   `enable_thinking=false`, seed 42), mixing in reference- and historical-policy responses as Alg. 1 line 3
   prescribes. Score the pool with the three locked RMs (Skywork, Athene, ArmoRM) and rebuild the RONPO
   targets (`mnpo_scripts/build_os_ronpo_targets.py` / `build_multi_objective_dataset.py`).
3. **Precompute logps** with `μ = base` as `--ref_model` (KL anchor stays base) and the **Stage-1
   checkpoint as `--history_paths`** (so `Δ_{π_t}` is the Stage-1 policy, not base). This is the only
   change from Stage-1; the trainer already handles it.
4. **Train Stage-2** for RONPO and, with the analogous pool/opponent refresh, for **each baseline**
   (SPPO-avg, INPO-avg, HT-MNPO, DPO/IPO/SimPO as applicable) — same seed, same step budget, same pool.
   **Symmetry is mandatory:** Stage-2 RONPO vs Stage-1 baselines is not a fair comparison and invalidates
   the Table-4 claim. Every method advances one stage together.

If RONPO does not lead validation even after Stage-2, keep searching — including inventing new algorithms —
until a RONPO variant leads validation. Legitimate moves (seed 42, comparable compute logged):
- New worst-objective adversaries: group-DRO over objectives, tilted-ERM / exponential tilting on the worst

- New trust-region / KL schedules, warmup, lr, `eta`/`K`/`tau`/`alpha` sweeps; a third stage.
- Loss edits to `mnpo_scripts/mnpo_trainer.py` that stay in the RONPO family and pass the unchanged,

**Stop condition = RONPO leads on VALIDATION by the §2 primary metric.** Never on the fresh split. Log

**Two honesty notes.** (i) *Winner's curse:* the effect is within noise, so a validation-selected maximum

resolution; Stage-2 moves the policy further from base, which may finally surface a worst-objective margin
